🎧 ResolveAI: Customer Support Agent

ResolveAI handles e-commerce support tickets end to end. It identifies the customer, classifies the issue, routes it, calls real back-office tools to investigate and act, checks every action against company policy, pauses for human approval when the stakes are high, and replies in the brand's voice.

Overview

Most support tickets are repetitive ("Where is my order?", "This arrived broken", "How do I return this?") but resolving them still means clicking through several internal systems. A plain chatbot can answer FAQs, but it can't do anything. ResolveAI is an agent: it has access to the order system, shipping tracker, knowledge base and refund API, so it can actually resolve the ticket.

Because it can take actions that cost money, the design centers on control: a deterministic policy engine sits between the agent and every write action, and anything outside policy goes to a human with the agent's reasoning and a pre-filled decision.

Problem

  • Agents spend most of their time on routine, multi-system lookups
  • Customers wait hours for answers that take seconds to find
  • Fully automated refunds without controls are a fraud and cost risk

What ResolveAI does

  • Resolves routine tickets end to end, in minutes
  • Takes real actions: refunds, replacements, return labels
  • Enforces policy in code, not just in the prompt
  • Hands off to humans with full context when needed

Complete workflow

Seven steps from incoming ticket to resolution. Read actions run freely; write actions always go through the policy engine.

  1. Intake & identify the customer

    Tool · Deterministic

    A ticket arrives from chat or email. Before any LLM sees it, card numbers and other sensitive data are redacted. The sender's email or session is matched to a customer with lookup_customer, which loads their profile, tier, recent orders and ticket history. If there's an existing open ticket on the same topic, the new message is threaded into it.

    InputRaw message, channel, sender identity
    OutputRedacted message + CustomerContext

  2. Triage & classify

    LLM · Structured output

    A fast model classifies the ticket into a strict schema: intent, extracted entities (order IDs, product names), urgency, sentiment, and whether it mentions anything high-risk like legal action, chargebacks or safety. Structured output makes the next step deterministic and easy to test.

    InputRedacted message + customer context
    OutputTriage JSON
    Triage schema 
    const Triage = z.object({
  intent: z.enum([
    "order_status", "damaged_item", "wrong_item", "return_request",
    "refund_status", "billing", "product_question", "account", "other",
  ]),
  entities: z.object({
    order_ids: z.array(z.string()),
    products: z.array(z.string()),
  }),
  urgency: z.enum(["low", "normal", "high"]),
  sentiment: z.enum(["positive", "neutral", "frustrated", "angry"]),
  risk_flags: z.array(z.enum(["legal", "chargeback", "safety", "fraud_signal"])),
  confidence: z.number().min(0).max(1),
});

  3. Route

    Decision · Rules

    Plain code, not the LLM, picks the path based on the triage result. Simple questions go to a lightweight FAQ path (knowledge-base answer only, no write tools). Order problems go to the order-issue agent. Anything with a risk flag, low triage confidence or a VIP angry customer goes straight to a human, with the triage summary attached.

    InputTriage, CustomerContext
    OutputRoute: faq · order_agent · human
    Router 
    function route(t: Triage, c: CustomerContext): Route {
  if (t.risk_flags.length > 0) return "human";
  if (t.confidence < 0.7) return "human";
  if (c.tier === "vip" && t.sentiment === "angry") return "human";
  if (["product_question", "account"].includes(t.intent)) return "faq";
  return "order_agent";
}

  4. Investigate & propose an action

    Tool use · Order agent

    The order-issue agent runs a tool loop. It pulls the order, checks shipment tracking, searches the knowledge base for the relevant policy article, and builds a picture of what happened. It can call read tools freely. When it decides on a fix (refund, replacement, return label, or just an explanation) it doesn't execute it directly: it emits a proposed action with a written justification.

    InputTicket, triage, customer context
    OutputProposedAction + evidence + draft reply
    Agent system prompt (excerpt) 
    You are ResolveAI, a support agent for {brand}.
Goal: resolve the customer's issue in as few back-and-forth messages as possible.
- Always look up the order before making any claim about it.
- Cite the knowledge-base article that justifies any action you propose.
- Write actions (refund, replacement, return label) are PROPOSALS. Call
  propose_action; a policy engine and possibly a human will decide.
- Never promise an outcome before the action is approved.
- If information is missing, ask the customer one specific question.

  5. Policy check

    Guardrail · Deterministic

    Every proposed write action is evaluated by a rules engine in code (see policy rules). It returns one of three outcomes: allow (execute automatically), needs_approval (send to a human) or deny (the agent must choose a different path and explain it). Putting this in code means a cleverly worded message or a prompt injection can't talk the agent into a refund it isn't allowed to give.

    InputProposedAction, order, customer history
    Outputallow · needs_approval · deny + reasons

  6. Human approval

    Human-in-the-loop

    For needs_approval, the agent's run is paused and persisted. A support lead sees a card in their queue: customer summary, what happened, the evidence (order, tracking, photos), the proposed action, the policy rule that triggered review, and the draft reply. They can approve, edit the amount or reply, or reject with a note. The agent then resumes exactly where it stopped.

    InputApproval card
    OutputDecision (+ edits / note), reviewer ID, timestamp
    Pause & resume 
    if (decision.outcome === "needs_approval") {
  await runs.save(run.id, { state: "awaiting_approval", messages, proposal });
  await approvals.create({ runId: run.id, card: buildCard(run, proposal, decision.reasons) });
  return; // worker is freed; nothing is held in memory
}

// Webhook from the approval UI:
async function onApproval(runId: string, review: Review) {
  const run = await runs.load(runId);
  run.messages.push(toolResult("propose_action", review)); // agent sees the human's decision
  await continueAgent(run);
}

  7. Act, reply & close

    Tool + LLM

    Approved actions are executed with an idempotency key, so a retry can never refund twice. The agent writes the final reply in the brand voice, stating only what actually happened (e.g. the refund ID and timeline). The ticket is updated with tags, resolution code and the full trace. A satisfaction survey goes out, and if the customer replies, the thread re-enters at step 1 with full history.

    InputApproved action, draft reply
    OutputAction executed, reply sent, ticket closed, trace logged

Policy rules

Evaluated in order; the first matching rule wins. Values are configurable per brand.

#ConditionOutcome
1Amount exceeds order total minus prior refundsdeny
2Customer has a fraud_signal flag or 3+ refunds in 90 daysneeds approval
3Order older than 30 days (non-defect reason)deny → offer store credit
4Refund or replacement value > $100needs approval
5goodwill reason over $20needs approval
6Everything else within policyallow

Why not just put this in the prompt? Prompts are guidance; code is enforcement. The agent is told the policy so it proposes sensible actions, but the policy engine is what actually decides.

Guardrails & evaluation

Guardrails

  • PII redaction before any model call
  • Scoped tools: the agent can only see the identified customer's orders
  • Policy engine gates every write action in code
  • Human approval above thresholds or on risk signals
  • Idempotent writes so retries never double-refund
  • Reply check: final message can't promise anything that wasn't executed
  • Turn limit: 3 failed attempts → hand off to a human

Evaluation

  • Replay set: 300 historical tickets with known correct resolutions
  • Routing accuracy and triage F1 per intent
  • Action correctness: right action and amount vs. human baseline
  • Policy-violation rate: target zero, tested with adversarial tickets
  • Escalation rate and approval-override rate (tracks drift)
  • CSAT and time-to-resolution in production
