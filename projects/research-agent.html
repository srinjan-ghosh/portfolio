🔎 DeepScout: Autonomous Research Agent

Ask DeepScout an open-ended question and it behaves like a small research team: a lead agent plans the investigation, spins up parallel search sub-agents, extracts evidence from what they read, writes a draft, has a critic agent fact-check every claim, and loops until the report is grounded and complete.

Overview

Research questions like "How do the leading approaches to grid-scale energy storage compare on cost and maturity?" can't be answered in a single LLM call. The answer depends on many sources, the path through those sources isn't known in advance, and a confident-sounding answer with no evidence behind it is worse than none.

DeepScout handles this with an orchestrator–workers design. A lead agent owns the plan and the final answer; short-lived searcher sub-agents each investigate one sub-question in parallel with their own context window; a critic agent checks the draft against the collected evidence and can send the lead back for another round.

Problem

  • Manual desk research takes hours of searching, reading and note-taking
  • Single-shot LLM answers hallucinate facts and citations
  • One long context fills up fast when reading dozens of pages

What DeepScout does

  • Breaks the question into independent sub-questions
  • Researches them in parallel, each in a clean context
  • Ties every claim in the report to a quoted source
  • Self-critiques and fills gaps before delivering

Complete workflow

Seven steps from question to delivered report. Each step lists its inputs, outputs, and the prompt or code that drives it.

  1. Intake & scope the question

    LLM · Lead agent

    The lead agent reads the user's question and decides whether it's specific enough to research. If key details are missing (time range, region, audience, depth) it asks up to two clarifying questions. Otherwise it writes a research brief that every later step refers back to.

    InputRaw user question, optional constraints (depth, deadline, format)
    OutputResearchBrief: objective, scope, out-of-scope, success criteria
    Research brief schema 
    class ResearchBrief(BaseModel):
    objective: str            # one-sentence restatement of the question
    scope: list[str]          # what must be covered
    out_of_scope: list[str]   # explicitly excluded
    audience: str             # e.g. "technical PM", "investor"
    depth: Literal["quick", "standard", "deep"]
    success_criteria: list[str]
    needs_clarification: bool
    clarifying_questions: list[str] = []

  2. Plan the research

    LLM · Lead agent

    The lead agent breaks the brief into 3–6 independent sub-questions that can be researched in parallel without depending on each other. It also sets a budget (search calls and tokens per sub-agent) scaled to the requested depth. The plan is saved to memory so it survives if the context window is later trimmed.

    InputResearchBrief
    OutputResearchPlan: sub-questions, search hints, per-agent budget
    Planner prompt (excerpt) 
    You are the lead researcher. Decompose the brief into 3-6 sub-questions.
Rules:
- Each sub-question must be answerable on its own (no dependencies).
- Together they must cover every item in brief.scope.
- For each, give 2-3 starting search queries and the source types to prefer
  (peer-reviewed, government data, industry reports, reputable news).
- Scale effort: quick = 3 sub-questions / 5 searches each,
  standard = 4 / 8, deep = 6 / 15.
Return JSON matching ResearchPlan.

  3. Parallel search sub-agents

    Tool use · Searcher ×N

    For each sub-question the orchestrator starts a searcher sub-agent with a fresh context window. Each one runs its own tool loop: search, open the most promising results, decide whether it has enough, refine the query, repeat. It stops when the sub-question is answered or its budget runs out. Running them concurrently cuts wall-clock time by roughly the number of sub-agents, and each agent's context stays focused on one topic.

    InputOne sub-question, search hints, budget
    OutputCondensed findings + list of source URLs actually read
    Orchestration code 
    async def run_searchers(plan: ResearchPlan) -> list[Findings]:
    tasks = [
        run_agent(
            system=SEARCHER_PROMPT,
            task=sq.question,
            hints=sq.search_hints,
            tools=[web_search, fetch_page, read_pdf],
            max_tool_calls=plan.budget.searches_per_agent,
        )
        for sq in plan.sub_questions
    ]
    # Sub-agents run concurrently; one failure doesn't sink the run.
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return [r for r in results if not isinstance(r, Exception)]
    Searcher agent loop 
    async def run_agent(system, task, tools, max_tool_calls, **ctx):
    messages = [{"role": "user", "content": render(task, ctx)}]
    for _ in range(max_tool_calls):
        resp = await llm.create(system=system, messages=messages, tools=tools)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return parse_findings(resp)          # agent decided it's done
        results = await execute_tools(resp.tool_calls)
        messages.append({"role": "user", "content": results})
    return await force_summary(messages)          # budget exhausted

  4. Extract evidence

    LLM · Lead agent

    Searcher findings are converted into atomic evidence records: a single claim, the verbatim quote that supports it, and the source it came from. Duplicate claims from different sources are merged (which raises their confidence), and conflicting claims are flagged rather than silently resolved. Records go into an evidence store the later steps can query.

    InputFindings from all searchers
    OutputEvidence store: Evidence[] + conflict list
    Evidence record 
    {
  "id": "ev_017",
  "claim": "Pumped hydro accounts for the majority of installed grid storage capacity worldwide.",
  "quote": "…pumped storage hydropower remains the largest source of …",
  "source": { "id": "src_04", "url": "https://…", "title": "…", "published": "2025-11" },
  "sub_question": "sq_1",
  "support_count": 3,
  "conflicts_with": []
}

  5. Synthesize a draft

    LLM · Lead agent

    The lead agent writes the report against the brief's success criteria, using only the evidence store. Every factual sentence carries an inline citation like [ev_017]. Where evidence conflicts, the draft presents both sides with their sources instead of picking one. Sections the evidence can't support are marked as gaps.

    InputBrief, plan, evidence store
    OutputDraft report with evidence IDs + explicit gap list
    Synthesis rules (excerpt) 
    - Use only facts present in the evidence store. Cite with [ev_id].
- No citation available? Either drop the sentence or mark it [GAP].
- When evidence conflicts, state both positions and cite each.
- Lead with a 3-5 bullet executive summary; then one section per sub-question.
- Prefer recent sources; note publication dates for time-sensitive figures.

  6. Critique & verify

    Decision · Critic agent

    A separate critic agent, with a different prompt and no stake in the draft, reviews it on four checks: grounding (does each cited quote actually support the sentence?), coverage (is every scope item answered?), balance (are conflicts represented fairly?) and freshness. It returns a verdict. On revise, its gap list becomes new sub-questions and the workflow loops back to step 3, up to two extra rounds.

    InputDraft, evidence store, brief
    Outputpass or revise + unsupported claims + new sub-questions
    Loop control 
    for round in range(MAX_ROUNDS + 1):        # MAX_ROUNDS = 2
    draft = await synthesize(brief, evidence)
    review = await critic(draft, evidence, brief)
    if review.verdict == "pass":
        break
    draft = remove_unsupported(draft, review.unsupported_claims)
    if round == MAX_ROUNDS:
        draft.add_limitations(review.gaps)   # be honest about what's missing
        break
    new_plan = plan_followups(review.gaps)
    evidence += extract(await run_searchers(new_plan))

  7. Report & deliver

    Output

    Evidence IDs are converted to numbered footnotes with titles, URLs and dates. The report gets an executive summary, a confidence rating per section (based on source count and agreement), a Limitations section listing any remaining gaps, and the full source list. It's delivered as Markdown and PDF, and the full run trace is saved for auditing.

    InputApproved draft, evidence store
    OutputFinal report (MD/PDF), source list, run trace

Guardrails & evaluation

Guardrails

  • Grounding-only synthesis: no evidence, no sentence
  • Citation check: the critic verifies each quote supports its claim
  • Budgets: per-agent tool-call caps and a global token/cost ceiling
  • Loop limit: at most 2 revision rounds, then report limitations
  • Source policy: domain deny list; prefers primary sources
  • Prompt-injection defense: fetched page text is treated as data, never instructions

Evaluation

  • Eval set: 40 research questions with reference answers
  • Citation precision: % of citations that truly support the claim
  • Coverage: % of scope items answered (LLM-judge + rubric)
  • Efficiency: tool calls, tokens and wall-clock per report
  • Regression gate: evals run on every prompt or model change

Design note: keeping the critic separate from the writer matters. A model reviewing its own draft in the same context tends to approve it; a fresh context with an adversarial prompt catches far more unsupported claims.
