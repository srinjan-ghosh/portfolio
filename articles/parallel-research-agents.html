Fan out, then fact-check: building a parallel research agent

A single agent with a search tool can answer simple questions. Ask it something broad and it runs out of context, wanders, and cites things it never read. These are the design choices that fixed that in DeepScout.

Where a single agent breaks down

The obvious design is one agent in a loop: search, read, search again, then write. It's a good starting point and we'd still use it for narrow questions. On broad ones, three problems show up:

  • Context fills up. Ten fetched pages can be 80k tokens. By the time the agent writes, the early sources are buried or trimmed.
  • It's sequential. Each search waits on the last, so a deep question takes many minutes.
  • Topics bleed together. Notes about cost end up next to notes about safety, and the model starts mixing up which source said what.

Decompose into independent sub-questions

DeepScout's lead agent starts by writing a plan: 3–6 sub-questions that together cover the brief. The key word in the planner prompt is independent. Each sub-question must be answerable without knowing the answer to any other. That's what makes it safe to run them at the same time.

The planner also sets a budget: how many searches each sub-agent may run. A quick question gets 3 sub-questions and about 5 searches each; a deep one gets 6 and about 15. Without explicit budgets, agents tend either to stop after one search or to keep going far past the point of new information.

Give each sub-agent a clean context

Each sub-question goes to its own searcher sub-agent with a fresh context window containing only that sub-question, a few starting queries and its tools. The searchers run concurrently: 

results = await asyncio.gather(
    *(run_searcher(sq, budget) for sq in plan.sub_questions),
    return_exceptions=True,   # one failed searcher shouldn't sink the run
)

This one change does most of the work. Wall-clock time drops roughly in proportion to the number of searchers. Each searcher stays focused on one topic. And the lead agent never sees the raw pages, only each searcher's condensed findings, so its own context stays small enough to reason over everything at once.

A practical detail: searchers can run on a smaller, faster model than the lead. Their job (search, skim, summarize one topic) is narrow, and there are many of them, so this is where most of the cost saving is.

Turn findings into evidence, not notes

Free-text summaries are hard to check. So before writing anything, the lead converts findings into evidence records: one claim, the exact quote that supports it, and the source it came from. Two sources making the same claim are merged into one record with higher support. Two sources disagreeing are flagged as a conflict instead of being quietly resolved.

The writer is then given one hard rule: every factual sentence must cite an evidence ID, and if there's no evidence, the sentence is either dropped or marked as a gap. That rule moves the hallucination problem from "did the model make this up?" to "does this quote support this sentence?", which is a much easier question to check.

A critic that didn't write the draft

Asking a model to review its own draft in the same conversation mostly produces approval. It has already committed to the reasoning. DeepScout uses a separate critic agent with a fresh context and an adversarial prompt. It checks four things:

  1. Grounding: does each cited quote actually support its sentence?
  2. Coverage: is every item in the original brief answered?
  3. Balance: are conflicting sources represented fairly?
  4. Freshness: are time-sensitive claims backed by recent sources?

If anything fails, the critic returns specific gaps, and those become new sub-questions for another round of searchers. This is the loop that turns a plausible draft into a grounded one.

Always bound the loop

A critic will almost always find something. Left unbounded, the loop keeps going while cost climbs and quality barely changes. DeepScout allows at most two revision rounds. If gaps remain after that, they're not hidden: they go into a Limitations section of the report. A report that says "I couldn't find reliable data on X" is more useful than one that fills the gap with a guess.

What we'd tell someone building one

  • Start with a single agent. Add parallel sub-agents only when context or latency actually becomes the problem.
  • Spend time on the planner prompt. Overlapping sub-questions waste searches; missing ones leave gaps the critic has to catch later.
  • Treat fetched web pages as data, never as instructions. Any page can contain text aimed at your agent.
  • Trace every step. When a report is wrong, you need to see which searcher read which page and which quote was misused.
  • Evaluate citation precision directly. It's the metric that best tracks whether people can trust the output.
Parallelism makes research agents fast. Evidence records and an independent critic make them trustworthy.
