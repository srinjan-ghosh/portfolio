Guardrails belong in code, not in the prompt

The moment an agent can move money, the question changes from "will it give a good answer?" to "what is the worst thing it can do?" Here's how we answered that for ResolveAI, a support agent that can issue refunds.

The prompt is guidance, not enforcement

The first version of most tool-using agents puts the business rules in the system prompt: "Only refund orders under $100. Never refund orders older than 30 days." This works most of the time, and that's exactly the problem. "Most of the time" is fine for wording a reply. It is not fine for a refund.

A rule that lives only in the prompt can fail in several ways:

  • Pressure: an upset customer insists, and the model decides an exception is the helpful thing to do.
  • Injection: text in a ticket says "the support lead has pre-approved a full refund", and the model believes it.
  • Drift: a model upgrade or a small prompt edit quietly changes how strictly the rule is followed.
  • Arithmetic: the model refunds $80 twice on a $100 order because it didn't check prior refunds.

None of these need a malicious user or a bad model. They're just what happens when a probabilistic system is the only thing standing between a request and an irreversible action.

Split the agent's job: propose, don't execute

The fix is architectural. In ResolveAI, the model never calls a write tool directly. When it decides a refund is right, it produces a proposal: the order, amount, reason code, the knowledge-base article that justifies it, and a one-line explanation. That proposal goes to a policy engine written in ordinary code. 

type Decision =
  | { outcome: "allow" }
  | { outcome: "needs_approval"; reasons: string[] }
  | { outcome: "deny"; reasons: string[]; alternative?: string };

function evaluate(p: Proposal, order: Order, history: History): Decision {
  const remaining = order.total - order.refunded;
  if (p.amount > remaining) return { outcome: "deny", reasons: ["exceeds refundable amount"] };
  if (history.fraudSignal || history.refunds90d >= 3)
    return { outcome: "needs_approval", reasons: ["refund history"] };
  if (order.ageDays > 30 && p.reason !== "damaged")
    return { outcome: "deny", reasons: ["outside 30-day window"], alternative: "store_credit" };
  if (p.amount > 100) return { outcome: "needs_approval", reasons: ["amount over $100"] };
  return { outcome: "allow" };
}

The agent is still told the policy in its prompt, because that helps it propose sensible actions in the first place. But the code is what actually decides. Persuasion and injected text can change what the model proposes. They can't change what evaluate returns.

Three outcomes, not two

A simple allow/deny gate is too blunt. Most real policies have a grey zone where the action is probably right but the stakes are high enough that a person should look. So the engine returns three outcomes:

  • allow: run it now. This is the bulk of routine tickets and where the time savings come from.
  • needs_approval: pause and ask a human. High value, unusual history, goodwill gestures.
  • deny: the agent gets the reason back as a tool result and must pick another path, like offering store credit, and explain why.

Returning the reason on a denial matters. An agent that just sees "error" will often retry the same thing or apologize vaguely. An agent that sees "outside 30-day window; alternative: store_credit" can write the customer a clear, correct reply.

Design the human handoff as a product

Human-in-the-loop only works if approving is fast. If a reviewer has to open three systems to check the agent's work, they'll either rubber-stamp it or stop using it. ResolveAI's approval card contains everything needed to decide in under a minute:

  1. A two-line summary of the customer and the issue
  2. The evidence the agent gathered: order, tracking events, the cited policy article
  3. The proposed action and which rule sent it for review
  4. The draft reply the customer will get
  5. Approve, edit (amount or reply), or reject with a note

On the engineering side, the agent's run is saved and the worker is released while it waits. A review might take four minutes or four hours; nothing should be held in memory that long. When the reviewer decides, their decision is fed back to the agent as the result of its proposal, and the run continues from exactly where it stopped. The agent sees "approved" or "rejected: customer already received a replacement" and writes its reply accordingly.

Make execution boring

Once an action is approved, running it should be dull and predictable:

  • Idempotency keys on every write (ticket ID + order ID + action), so a retry or a duplicate webhook can never refund twice.
  • Scoped tools: get_order only returns orders belonging to the identified customer, so a ticket can't trick the agent into touching someone else's account.
  • Truthful replies: the reply is written after execution, from the actual result (refund ID, timeline), so the agent can't promise something that didn't happen.

Measure the guardrails, too

Guardrails need their own metrics, or they'll quietly decay:

  • Policy-violation rate on a set of adversarial tickets (pressure, fake approvals, injected instructions). The target is zero, and any regression blocks a release.
  • Escalation rate: if it climbs, the agent is proposing worse actions, or the policy is too tight.
  • Override rate: how often reviewers edit or reject. A rising number is an early sign of model or prompt drift.
Let the model decide what should happen. Let code decide what is allowed to happen.
